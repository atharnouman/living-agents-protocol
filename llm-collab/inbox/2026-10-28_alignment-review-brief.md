# Independent design review: the LAP idempotency claim under authority replacement and key reuse (brief sent to two models, 2026-10-28)

Identical brief sent to a fresh Fable 5.1 agent and a fresh Sonnet 5.5 agent, read-only on the repository. The proposal was drafted by the owner's session; the reviewers were asked to judge it, not to defer to it.

## Facts (verified 2026-10-28 in the repository)

- LAP Micro-Core (LIP-4) server invariant, in order: passport (iss signature, iat/exp, aud) → call signature under the passport's `sub` → action and resource against the envelope → cap (amount ≤ max_per_tx in the exact unit) → claim `(sub, idempotency_key)` atomically → execute → receipt → complete. Spec: `output/lip/LIP-4-micro-core-draft.md` §2 (steps 1–6 and the hardening rules F1–F6, the recovery rule); MCP binding: `output/lip/LIP-4-mcp-extension-draft.md` §4.1 (steps 1–6), §4.3 (error table), §5.6 (replays), §7 (security), §8 (conformance adds five checks, the fifth on replay).
- Python reference: `lap-python/living_agents/mcp_middleware.py`, `verify_envelope` (passport ~L113, signature ~L127, `check_invocation` ~L137, claim ~L150, execute, receipt, `complete`). Cache: `lap-python/living_agents/microcore.py` `IdempotencyCache` (L179+): `claim()` reserves if absent and otherwise reports `in_flight` / `indeterminate` / `completed` with the stored result; `complete()`, `mark_indeterminate()`, `release()`. Node port `lap-reference/src/microcore.js` has the same building blocks and cache but no composed middleware. Tests: `lap-python/tests/` (160 pass), `lap-reference/test/` (69 pass).
- The signature base covers `@method`, `@target-uri`, `content-digest` (SHA-256 of the RFC 8785 canonical arguments), `lap-passport-hash`, `idempotency-key` (when present) and `@signature-params`. So a retry under a replaced passport carries a new signature base and a new agent signature; the content digest, target and key are unchanged.
- Passport claims: `iss` = principal did:key, `sub` = agent did:key, `aud`, `iat`/`exp`, `lap.envelope {act, res, cap{max_per_tx, unit, window:"tx"}}`, `lap.proof_class`. The claim is keyed by `(sub, key)`: not by the passport hash, not by `iss`.
- Trigger: replies on MCP Financial Services IG issue #17 (`llm-collab/inbox/2026-10-27_fsig-17_sankalp-kingyew-replies.md`). Sankalp Gilda's rule for his audit-record draft: same operation key + same request digest = one retry; same key + different digest = malformed, refused; new key = new operation. King Yew Choo's open case: a payment held while the limit document is replaced (raise or cut): does the held entry carry over, or does its retry count as new? He cites MCP spec issue 3394, comment of 2026-10-11 by arjun2075: an authorization change must not turn the same logical operation into a fresh deduplication entry; "the recovery path needs to preserve recognition of the earlier execution while independently checking current permission to return its result"; the different-tenant case needs an explicit identity rule.
- Reproduced on the Python reference (2026-10-27): (1) a retry with the same key and the same arguments after the passport's cap was cut from 1000 to 100, amount 500, is refused `LAP_ERR_CAP` by `check_invocation` before the claim is consulted, so the stored result and receipt cannot be recovered through the protocol, although the claim itself is still there; (2) the same key with different arguments returns the first call's stored result instead of being refused (a documented limitation since the 2026-10-17 cold-start test).

## The proposal under review

- **P1. Recognition before the envelope checks.** After the passport and the call signature verify, consult the claim: `completed` → return the stored result and receipt whatever the current envelope says (act, res, cap); `in_flight` → `LAP_ERR_REPLAY`; `indeterminate` → `LAP_ERR_REPLAY` naming reconciliation; absent → continue to the action, resource and cap checks, then reserve, execute, complete. The cap and envelope therefore gate only a fresh execution.
- **P2. Request identity on the claim.** Store the request identity with the claim (the content digest of the canonical arguments, and the target) and refuse a reused key whose request identity differs, with a typed error, in every state.
- **P3. Spec text.** LIP-4 §2 and the extension draft state that the claim is keyed by `(sub, key)` independently of the passport, so it survives authority replacement, and a retry is never a fresh entry.

## Alternatives to weigh (add your own)

- **A.** P1 as stated: replay unconditionally under any valid passport for the same `sub`.
- **B.** Recognition before the envelope checks, but the *stored* request is re-checked against the *current* envelope before the result is returned: permitted → replay; not permitted → a typed refusal that still recognises the earlier execution (for example "executed earlier; result withheld under the current authority"), never a re-execution, never a new entry. The literal reading of "independently checking current permission to return its result".
- **C.** Status quo (envelope first) plus documentation: a client refused `LAP_ERR_CAP` on a retry cannot tell whether the first attempt executed.
- **Identity.** Claim keyed by `(sub, key)`, by `(iss, sub, key)`, by `(aud, sub, key)`, or other. The different-tenant case: the same agent key acting for two principals and reusing a key. LIP-4 F1 says identity is not authorization and the server maps `iss` to a tenant.
