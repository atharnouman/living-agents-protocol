## Recommended rule set (LIP-4 §2; extension §4.1)
1. Passport: iss signature, iat/exp, aud, issuer list, proof floor. 2. Call signature under `sub`; `idempotency-key` covered when present. 3. **Recognise:** look up (tenant, sub, key), tenant = the server's F1 mapping of the verified `iss`, default normalised `iss`. Identity differs → `LAP_ERR_IDEMPOTENCY` in every state. Completed → stored result and the same receipt, no execution, no new receipt. In flight → `LAP_ERR_REPLAY`. Indeterminate → `LAP_ERR_REPLAY` naming reconciliation. Absent → continue. 4. act/res. 5. cap. 6. Atomic `claim(scope, key, identity)`, re-dispatching on every status (a twin may have completed meanwhile). 7. Execute, receipt, complete.
Consequence to state: `LAP_ERR_CAP`/`ACT`/`RES` on a retry now means "no execution recorded under this key" (given a shared store, F6), which dissolves option C's ambiguity.

## Answers
**1.** Adopt A with the rule above; reject B and C. The envelope bounds *effects*; a replay has none, and the result is evidence of an effect that happened under authority valid at the time. Withholding it (B) defeats the recovery path and the dual-held log (§3), exactly where the retry case leaves it one-sided. Narrowed or replaced: disclose. Expired: `LAP_ERR_EXPIRED`, nothing disclosed; reissue and retry with the same key is the designed path. Define "current permission" as: the caller currently authenticates under a valid passport for the same tenant and agent key, accepted by server policy, and signed this exact identity. It is not the cap, nor act/res. A server MAY apply a stricter disclosure policy under F1, but then answers with a typed refusal naming the earlier execution, never `LAP_ERR_CAP`. Audit: the receipt binds request and response hashes only, so it verifies under the new passport (case 7); the stored completion SHOULD record the executing passport hash and time; add an optional `replay: true` in the result `_meta` (compatible under §6; content, structuredContent and receipt unchanged, so §5.6 still holds).
**2.** Scope (tenant, sub); the store is per server identity, and one shared across audiences adds `aud`. Different tenant, same sub and key → absent → fresh path: never a replay, never a mismatch error, no leak. Principal key rotated but mapped to the same tenant → recognised; (iss, sub, key) would double-execute there. The passport hash never enters the identity (3394's epoch warning).
**3.** Identity as above, compared before state. In flight or indeterminate with a different identity → `LAP_ERR_IDEMPOTENCY`, not `REPLAY`, or the client waits on an operation that is not its own; the recovery rule's "keep the same key" covers only the *same* intended execution. Leak: only "this tenant and agent used this key", to a caller who proved the agent key; acceptable. Aligns with draft-ietf-httpapi-idempotency-key-header-08 (2026-10-22): 422 for reuse with a different payload, 409 while outstanding; it defines no problem-type names and leaves retention to the server, which "SHOULD define such expiration policy and publish it". Sankalp's cases map: same key and digest → replay; same key, other digest → refused; new key → executes (his control).
**4.** Signature before recognition: F2, and the key and digest lines are trusted only once the base verified. Passport before recognition: nothing to an unauthenticated caller. A replay returns the stored result and the same receipt. Atomicity: the lookup is a plain read; `claim()` stays the single atomic reserve-or-report; reserve-then-abort would break §4.1's "no claim consumed on failure". API, Python: `lookup(scope, key, identity)` and `claim(scope, key, identity)` → `absent|reserved|completed(result)|in_flight|indeterminate|mismatch`; `complete`, `mark_indeterminate`, `release` keep their shape; `scope=(tenant, sub)`, `identity=(method, target, content_digest)`; rename the stored "receipt" to `result`. ## Overclaims or errors in the proposal
1. "Keyed by (sub, key), not by iss" presented as sound: case 5 shows it replays across principals.
2. "A retry is never a fresh entry": true only within one tenant scope; across tenants it must be fresh.
3. P1 omits the identity check before the stored result is returned.
4. Cross-tool key reuse through a shared cache (case 4) unmentioned; the README pattern invites it.
5. §7's eviction sentence left standing, though it contradicts P1 and P3.
6. Identity stored at completion would not fix the reconciled receipt; it must be stored at reservation.
7. "Both ports" overstates Node, which has the cache only.
8. Q4's atomicity worry is misplaced: `claim()` already is the atomic step; only a read is added.
9. A new `LAP_ERR_KEY_REUSE` would trip extension §6.
10. The legacy `check`/`store` API would bypass P2 unless retired.
