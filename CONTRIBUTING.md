# Contributing to the Living Agents Protocol

Thanks for your interest. This project runs lean and evidence-first; here is how to engage.

## The LIP process

Protocol changes happen through **LIPs** (LAP Improvement Proposals), the numbered drafts in `output/lip/`. To propose a change: open an issue describing the defect or improvement with a concrete failure scenario, or a PR amending a LIP draft. Normative text uses RFC-2119 keywords and separates **Normative** rules from *Informative* rationale — keep that discipline. The scope fence (founding document §3/§12) is real: additions outside the ten admitted concerns need to argue past the fence's amendment rule, not around it.

## Code

`lap-reference/` is deliberately **zero-dependency** (Node ≥ 20 built-ins only) — PRs adding dependencies will be asked to justify existence-level necessity. Run the suite with:

```bash
cd lap-reference && node --test test/
```

Every mechanism change needs tests, and anything touching the algebra needs adversarial cases (see `test/round3.test.js` for the style). The deterministic cross-language vectors in `output/lip/test-vectors/` are regenerated by `generate_vectors.py`; if your change alters canonical forms, regenerate and explain why.

## Review culture (read this — it's the project's signature)

This spec was hardened by structured adversarial review across multiple frontier AI models before any human community saw it: four rounds, ~140 verified findings merged, with every external claim verified before merging and **rejections logged with reasons** in `llm-collab/IMPROVEMENTS-LOG.md`. The same standard applies to human contributions: findings need evidence or a failing case; flattery and vibes-based objections score zero; and being wrong with a concrete example is worth more than being vague and safe. If you want to run an AI-assisted review yourself, the kit in `llm-collab/` is the instrument — **treat it as read-only and deliver findings as new files in `llm-collab/inbox/`** (two in-place file corruptions by review tools taught us this rule).

## Provenance

Releases are OpenTimestamps-anchored to Bitcoin (`output/anchors/`). If you need to prove what this repository said on a given date, the `.ots` proofs beside each artifact are the mechanism.
